## Windows decline — exact attribution

**The 2026-08-20 → 2026-08-28 `C:` free-space decline (43.07 GB → 18.8 GB, ≈24.27 GB) is primarily disposition B: MockingBird development/test-tooling accumulation. It is not a defect in the shipped product.**

Dated, quantified evidence (directory creation/modification timestamps read directly from the real Windows filesystem, cross-referenced against the exact 2026-08-20 14:00 → 2026-08-28 window):

- **Runtime-cache entries created in-window: ≈10.3 GB** (`68f9d23f…` 2.53 GB @ 08-20 14:00, `25947a36…` 2.52 GB @ 08-26, `b9bdcee9…` 2.52 GB @ 08-25, `d3db48b6…` 2.52 GB @ 08-28 15:33 — the runtime hash for the same-day redeploy of accepted HEAD `80e1bb3`, `e9ae6be8…` 205 MB @ 08-25).
- **Acceptance-recorder output created in-window: ≈7.3 GB** (`20260820T222528Z` 3.46 GB @ 08-20 19:55, `20260821T152817Z` 3.85 GB @ 08-21 13:16 — both real recordings from genuine daylight/dusk acceptance attempts; nothing further was added by the recorder after 08-21, consistent with the 08-25/08-26/08-28 attempts each independently recording "no live Observation session ran").
- **Combined, directly dated: ≈17.6 GB — roughly 72% of the observed 24.27 GB decline**, attributable to two dev/QA-tooling growth paths, both structurally distinct from anything a real end-user installation does.
- **Release directories created in-window: ≈165 MB** (6 releases × ~27 MB) — confirms, independently, the 2026-08-28 report's own prior conclusion that retained release artifacts cannot explain the decline.
- **The remaining ≈6.7 GB (≈28%) is not individually dated to this window** and is not force-fitted to a single cause: plausible contributors include further `userdata/` backup growth (see below), model-bundle re-caching across sessions using different `--skip-*`/`--*-bundle-source` flag combinations, or ordinary background Windows/software usage (Docker Desktop measures 24.4 GB and `ProgramData` 23.2 GB on this machine — both large, pre-existing, but **not shown to have grown specifically in this window** and not chased further, per the brief's own instruction not to solve every storage problem here). Disclosed honestly as unattributed rather than forced to a round number.

**Why this is disposition B and not A.** `deploy_windows_dev.py`'s own constants and docstrings are explicit that this tool, and everything it writes under `%LOCALAPPDATA%\MockingBirdDev`, is dev/test-only — "a sibling of the real production `%LOCALAPPDATA%\MockingBird` ... never the same directory" (`deploy_windows_dev.py:111-116`). The real production upgrade path (closed by the already-accepted Release Engineering Foundation v1) works differently in kind, not merely in scale: "replace the app, relaunch" in place, with exactly one pre-migration database-level safety backup as its only retained-history mechanism (`docs/release-engineering-foundation-v1-report.md:346-349`) — there is no content-hash-keyed, multi-version runtime cache anywhere in the real product's own update story. A real end-user installation cannot reproduce this growth pattern by construction; it is unique to this project's own dev-hardware-acceptance workflow, used dozens of times across the last five weeks' worth of milestones (per this project's own extensive session history).

**The growth path itself was not a hidden defect — it was a known, disclosed, deliberately-deferred gap whose real-world impact had been mis-judged.** `docs/windows-dev-deployment-design.md`'s own "Left for follow-up" section (written when the caching mechanism was designed) states: *"Cache garbage collection. `--keep` bounds *release* directories only; a runtime/model cache entry no retained release still references is never automatically removed. Given the cache is small in count (one entry per distinct dependency/model version actually built, not per commit) this is unlikely to matter in practice."* Real measurement in this milestone falsifies that specific "unlikely to matter" judgment: five-plus weeks of active Windows-packaging work (onnxruntime CUDA DLL fixes, BioCLIP durable-deployment work, detector-promotion benchmarking, several dependency-pin fixes) produced enough distinct runtime hashes, never pruned, to reach 38.5 GB — the largest single consumer found in this entire investigation, on either side of the WSL/Windows boundary. This is fixed below (see "Fixes").

## WSL / Windows boundary

- The dev checkout's own `data/backups/`/`data/models/`/`.venv`/tool-cache growth (≈32 GB combined) lives entirely inside the WSL2 virtual disk, whose backing `ext4.vhdx` file is on **`E:`**, not `C:` — confirmed directly via the Windows registry. **None of this WSL-side growth is implicated in the observed `C:` decline**, and per the governing brief's own instruction, is not classified as a released-product defect: the native product does not create the same condition (a real Windows install has no WSL layer at all).
- Deleting a file inside WSL does **not** immediately return capacity to the Windows host in general (the classic WSL2 dynamically-expanding-vhdx behavior — the `ext4.vhdx` measured at 283 GB on disk against only 125 GB of real content is direct, current evidence of exactly this on this machine) — but because this vhdx sits on `E:`, not `C:`, that specific behavior is orthogonal to the milestone's central question and is reported for completeness, not as a finding requiring product action.
- The one place WSL and the observed `C:` decline *do* interact is indirect: this project's own dev-acceptance workflow (real WSL Python driving `powershell.exe` interop against the real Windows host) is what populates `%LOCALAPPDATA%\MockingBirdDev` in the first place — the growth mechanism lives in dev tooling invoked from WSL, but the bytes it deposits are genuinely on `C:`, which is why the attribution above is correct as stated.

## Storage contract (durable / evidence / cache / temporary / model-asset classes)

Traced from `src/mockingbird/repository/product_repository.py`'s real retention-eligibility code (`_storage_retention_evaluation`, `storage_summary`) and `docs/appliance-storage-privacy-recovery-v1-contract.md` (accepted 2026-08-23, the canonical design record for this whole area — reconciled and re-verified against current code in this milestone, not re-derived from scratch):

**Durable truth/state (SQLite; never touched by retention).** `mockingbird.sqlite3` — Reviewed truth (`ReviewLabel`), Visit/Event/Observation records, Source/Stream/Zone configuration, user/auth state (including schema v58's `field_acceptance_credentials`), Place settings, retention configuration itself. Confirmed structurally: grepping the entire ~2,000-line storage-retention section of `product_repository.py` for `delete(VisitModel)`/`delete(EventModel)` returns zero matches — retention removes evidence *files* and *links*, never a Visit/Event/ReviewLabel row.

**Durable evidence.** Selected/canonical evidence media referenced by an active Visit's primary frame (`active_visit_primary_evidence`), any still-unreviewed Visit's evidence (`unresolved_visit_evidence`, structurally coerced protected — the one lever the API cannot override even if a caller tries), reviewed-wildlife secondary evidence by default, and — a real finding this milestone made, see below — user-imported evidence (manual/folder import), currently protected unconditionally regardless of age or review state.

**Regenerable/cache.** No persisted thumbnail/derived-preview artifacts exist in the live runtime today (confirmed, not merely asserted, by the accepted Aug-23 contract and re-confirmed this milestone — only an in-memory PIL resize and an offline dev tool exist). `derived_media_reference`/`crop_revision_history` (activity/refined crops) are the one real derived-asset shape, and are protected, not treated as disposable, since they carry review-relevant information.

**Temporary.** Acoustic working segments (`MediaAssetModel.acoustic_working_segment`) via an independent, always-on 15-minute sweep (`run_working_audio_retention_sweep`), deliberately file-then-row-delete (opposite ordering from the general cleanup pipeline — see "Retention correctness," below, for why that's the *correct* choice for genuinely disposable temp data). Storage-cleanup's own quarantine directory (`.recovery/<batch_id>/`) is the "upload staging"-equivalent for this subsystem — a 14-day recoverable holding area, not a bug.

**External/model assets.** MDv5a, BioCLIP-2, optional BirdNET, and their runtime/framework caches — required product footprint, not owned by retention at all (see "Models and caches," below, for the Windows-side measured split of required-vs-dev-only footprint).

Retention does **not** treat these interchangeably: eligibility is computed per-category via a mutually-exclusive `if`/`elif` ladder (`_storage_retention_evaluation`), independently confirmed by re-running the full, real (mostly filesystem-backed, not mocked) test suite for this subsystem — **349 tests, 0 failures** (see "Validation," below).

## Retention correctness

Answering the governing brief's 14 questions, reconciled against real code and a live, independently re-run test suite (`tests/test_storage_retention*.py`, `tests/test_saved_media_*.py` — 349 tests total across the whole storage/retention/backup/doctor family, all passing):

1. **Eligible for automatic deletion:** orphaned managed media (no Visit/non-Visit reference, ≥30d default), rejected/suppressed-analysis-only media (opt-in age lever, `None`/protected-forever by default), reviewed non-primary secondary evidence (≥180d default; wildlife variant only if the operator explicitly disables `retain_reviewed_bird_wildlife_evidence`), and evidence whose every referencing Visit is fully superseded (≥90d default).
2. **Never automatically deleted:** reviewed truth rows, Visit/Event/Observation rows, export manifests, backups (explicit non-goal, confirmed intentional — see "Backup interaction"). This is application-level filtering (an `if`/`continue` ladder), not a DB-level immutability constraint — except `retain_unresolved_visit_evidence`, which the API layer structurally coerces to `True` regardless of what a caller sends, a deliberate, code-enforced exception to "just a filter."
3. **Unreviewed Visit:** fully protected, unconditionally, no age-out lever at all, both primary and secondary frames.
4. **Reviewed truth:** primary frame protected forever; secondary frames age out per policy (never before 180d by default) **without ever mutating the truth row itself** — proven by an explicit before/after truth-table-diff test.
5. **Evidence deleted while DB references remain:** only ever in the deliberate, audited case of a *permanently purged* (post-14-day-quarantine) batch — the file is gone, the `MediaAssetModel` row is kept forever as an audit trail (mirrors `StorageCleanupItemModel.original_local_path`'s own retained-forever convention), and every media-serving read path already handles a missing file as a clean 404, never a crash.
6. **DB records disappear while media remains orphaned:** not possible in the general cleanup pipeline (no `MediaAssetModel` row is ever deleted there). The one place a real deletion happens (`run_working_audio_retention_sweep`) deliberately deletes the file *first*, DB row second, precisely to avoid this — its own docstring names the tradeoff explicitly: *"the opposite order would risk a silent orphaned file (undiagnosable disk growth) on a partial failure, which is exactly what this sweep exists to prevent."* A crash between those two steps leaves a row pointing at an already-deleted file for at most one 15-minute sweep cycle (self-healing, not permanent).
7. **Imported/manual-media Visits:** a **real, previously-undocumented-as-wrong finding** (below) — currently protected *unconditionally forever*, not "the same rules as any other Visit-linked evidence" as the accepted Aug-23 contract claims.
8. **Archived cameras/Sources:** no special treatment at all — confirmed by grep across the whole retention section; eligibility depends only on Visit-linkage/age/review state, never Source status.
9. **Backups:** never referenced anywhere in the retention code (confirmed by grep) — a confirmed-intentional non-goal, not an oversight (see "Backup interaction").
10. **Temp files cleaned after success:** the "temp" state for this pipeline *is* the 14-day recoverable quarantine, by design — not cleaned immediately on purpose.
11. **Temp files cleaned after failure:** each item processes in its own transaction; one item's exception never stops the batch or corrupts siblings; a post-loop reconciliation pass re-derives true batch state from actual persisted state **and** a live filesystem check, never trusting in-memory loop state alone.
12. **Idempotent:** yes, at three independent layers (execute/restore/purge), each keyed by an explicit idempotency key checked before any mutation, proven by a dedicated repeat-and-compare test.
13. **Safe if interrupted:** yes for data-integrity (every already-committed item is stable; the in-flight item safely reverts) — with one real, narrow, disclosed gap: a batch left in the rare `"staging"` (interrupted) state can only ever be *restored*, never purged, by any path, even manually past its recovery deadline (see "Remaining risks" — bounded to lost disk space, never data loss, since restore always works).
14. **Transactional where product truth requires it:** yes, precisely traced — file-move happens inside an open DB transaction; DB link-removal only follows a *confirmed-successful* move, both committing together; the one place ordering is deliberately reversed (`run_working_audio_retention_sweep`) is correct for that pipeline's own different risk profile (temp data, never evidence).

### Real finding: imported media is over-retained relative to its own documented contract

`create_media_import`/`import_folder_media` both funnel through `_create_media_product_records`, which sets `VisitModel.representative_media_path` but — confirmed by grepping every `VisitEvidenceLinkModel(` construction site in the file — **never creates a `VisitEvidenceLinkModel` row**. `_storage_retention_evaluation`'s `legacy_representative_evidence` guard protects any asset whose `representative_media_path` matches but has no link — which is *every* imported asset, permanently, regardless of the owning Visit's review state or even an explicit `is_superseded=True`. This was verified empirically (not just read): a script constructing an imported asset, rewriting its age to 10 years, setting maximally permissive retention thresholds, and marking the Visit superseded still leaves it protected with `eligible_media_count == 0`.

This directly contradicts `docs/appliance-storage-privacy-recovery-v1-contract.md:159-163`'s explicit claim that imported originals are "subject to the same active/superseded/reviewed rules as any other Visit-linked evidence — no separate contract." That claim was not previously verified by any test — grepping the entire `test_storage_retention*.py`/`test_saved_media*.py` family for `create_media_import`/`import_folder_media` returns zero hits.

**Why this is disclosed, not fixed, this milestone.** The failure direction is safe: MockingBird already keeps too much (never loses truth), and imported media is this project's own promoted, default, camera-less acquisition path (per the accepted Whole-Product UI / Accessibility / Performance Closure v1 report), so the growth this causes is real but bounded by how much a given install actually imports — not unbounded relative to product use. A correct fix needs either a real `VisitEvidenceLinkModel` for imported media (a materially larger change to Visit-creation semantics, out of this bounded milestone's scope) or a narrower change teaching `legacy_representative_evidence` to also respect `is_superseded` the way `superseded_only_evidence` already does for linked evidence — the more surgical option, but one that touches retention *eligibility* logic (the highest-stakes code in this entire subsystem) with **zero pre-existing test coverage for this exact path** to catch a regression. Given the current behavior causes no data loss and is not release-blocking, this milestone disclosed it precisely (with an exact repro) rather than rush a fix to eligibility logic under time pressure — matching this project's own established precedent for exactly this class of finding (several similar items in the accepted Aug-23 contract's own "Known bounded gaps" section were disclosed, not fixed, on the same reasoning).

## Orphans

**Database → missing media.** Handled gracefully today: `_storage_managed_media_path` returns `None` for any asset whose file can't be resolved, and every consuming path (the storage scan, Doctor's own sampled Media Integrity check) skips or reports it rather than crashing; the direct media-serving API route returns a clean 404. Doctor's Media Integrity check (`doctor.py`) samples the 25 most-recently-created rows for exactly this condition — cheap, stat-only, sampled by design (never claims a file "decodes," only that it exists and is non-zero-length).

**Media → no database owner.** A real, structural gap, precisely characterized: **no code anywhere in this codebase scans the media directory itself and cross-references it against the database.** Every retention/integrity/summary function — including Doctor's own missing-file check above — is a DB-row walk (does this known row's file exist?), never the reverse (does this file have a DB owner?). The only full directory walk anywhere in the tree is `backup.py`'s own `_discover_media_files` (`media_root.rglob("*")`), used purely to archive every file it finds into a backup, orphans included, with zero DB cross-reference.

**Does this actually occur, and does it accumulate materially?** The accepted Concurrent Candidate Visit Persistence Reliability v1 milestone already disclosed a bounded orphan-media possibility (a filesystem write surviving a rolled-back SQLite transaction on a failed-then-retried candidate-Visit attempt). This investigation traced it precisely and found one correction worth recording: the report's own "bounded — one small file per failed attempt" characterization understates the real per-attempt bound slightly (the evidence-persist loop can write and flush up to 4 files, per `_DEFAULT_MAX_EVIDENCE_ITEMS_PER_CANDIDATE`, before any of several later flush points fails) — still small and bounded, not unbounded. The one concretely-captured failure mechanism in that report's own evidence actually fires *before* any media write in the current code path (confirmed by exact line-order tracing), so it produces zero orphans by itself; the true orphan-producing timing (failure strictly between a media write and commit) remains a real, traced-but-not-live-reproduced code path, consistent with why real "database is locked" contention needed artificial multi-process stress to reproduce at all in that milestone's own work.

**Existing cleanup does not, and cannot, identify these** (structural — see above), so any orphan that does occur is permanently invisible and unreclaimed, not merely uncommon. Per the governing brief's own instruction, this is not reopened here (no concrete storage defect was reproduced beyond what was already disclosed and accepted) — it is disclosed precisely as a real, bounded, low-materiality, permanently-non-self-healing gap in "Remaining risks," a reasonable candidate for a future bounded "sampled orphan sweep" (mirroring Doctor's own sampled-integrity-check shape) rather than a fix rushed into this milestone.

## Pressure behavior (healthy / warning / critical)

**Already built, tested, and materially more complete than `docs/roadmap.md`'s own text currently credits.** `LocalStorageDiskStatus.storage_health_tier` (`src/mockingbird/storage/database.py`) is a real, graduated four-tier ladder — `healthy` / `getting_low` / `action_recommended` / `critical` — with concrete, code-real thresholds (not invented for this report):

| Tier | Free bytes | Free ratio |
|---|---|---|
| `healthy` | ≥ 5 GB | ≥ 15% |
| `getting_low` | < 5 GB or < 15% | |
| `action_recommended` | < 1 GB or < 5% | |
| `critical` | < 200 MB or < 1% | |

Wired into `StorageSummary`, `ProductHealthStatus`, `/api/product/health`, and Doctor's Storage check — 16 tests in `tests/test_storage_status_disk.py` (independently re-run this milestone, all passing) exercise the exact boundary logic including the ratio-vs-absolute-floor interaction on both very large and very small disks, and the deliberate "0/0 (probe failed) never fabricates alarm" edge case. `docs/roadmap.md`'s framing ("does not yet implement the full four-state escalation") is accurate about the missing *behavioral* piece (see next paragraph) but somewhat undersells how much real, tested, threshold-driven *detection* already exists — recorded here as a documentation nuance, not a defect.

**What is genuinely still open, confirmed by direct code tracing of both the evidence-write and SQLite-write paths:** no write path anywhere consults `storage_health_tier`/`is_low_space` before proceeding. A disk-full condition is not specially detected or guarded against — it is simply allowed to raise a real `OSError`, exactly like any other filesystem failure. This is a real gap in the "insufficient for new evidence" sense the governing brief asks about, but it is not a release-blocking correctness defect: it does not violate any of the brief's own explicit prohibitions (see next section).

## Behavior under low space

Verified directly against real code (not the roadmap's own summary), for every listed concern:

- **No corrupt database writes:** SQLite's own transactional semantics (already proven under the accepted transactional-DDL migration hardening and the Concurrent Candidate Visit Persistence milestone) mean a disk-full write raises and rolls back — never a partial/corrupt commit.
- **No silent Visit loss:** a disk-full evidence write raises an `OSError`, caught by the same generic exception handler that already correctly fails a whole candidate-Visit attempt atomically (already-proven transactional, from the accepted Concurrent Candidate Visit Persistence Reliability v1 milestone) — the attempt fails visibly (an error, not a fabricated success), and nothing already-committed is touched.
- **No partial truth presented as success:** confirmed by the same transactional tracing above, and by the storage-cleanup pipeline's own reconciliation-not-trust-in-memory-state discipline (see "Retention correctness" §11).
- **No endless retry storms:** confirmed by tracing the actual retry classification — only the specific, narrow SQLite lock/busy code gets the bounded (3-attempt) caller-side retry; a plain `OSError` (disk-full) falls into the separate, non-retried generic-failure path. Retrying a write against a genuinely full disk would itself be a retry-storm risk; not retrying it is the *correct* behavior, not a gap.
- **No disk-filling logs:** see "Logs," below — the Host's own log is hard-bounded; the one still-open unbounded-log-adjacent item (Camera Node journald) is a pre-existing, already-disclosed, deliberate scope decision from an earlier milestone, not new.
- **No uncontrolled capture continuing until the filesystem fails:** every real write path already fails closed (raises) rather than silently swallowing an `OSError` — confirmed by direct code reading of `_write_media_file`/`_copy_media_file` and the SQLite engine/session construction path.

**Why a write-path low-space guard was not added this milestone.** Doctor's existing polling-based `storage_health_tier` check already independently satisfies the brief's own "the product communicates pressure" requirement — a user checking Product Health sees the graduated warning regardless of whether any specific write has yet failed. Adding a pre-write guard would only change *when* a doomed write is refused (proactively vs. reactively), not *whether* truth is protected (it already is, either way, per the transactional tracing above) — this is exactly the "if current product health already covers this correctly, prove it rather than redesign it" case the governing brief names, not a silently-accepted gap.

## Product health / Doctor

Doctor already covers storage health substantially — re-confirmed, not redesigned, this milestone (20 targeted tests re-run clean): the four-tier disk ladder above (critical always reads `WARN`/`DEGRADED`, never silently `PASS` — the literal "reports healthy at 99% full" failure mode does not occur, confirmed by both code tracing and a passing dedicated test), backup staleness/unreadability/interrupted-restore detection (`BACKUP_STALE_AFTER_DAYS = 30`), and a sampled Media Integrity check for missing files. Two real, precisely-scoped gaps found, both disclosed rather than fixed (neither release-blocking):

1. **No Doctor signal for automatic-cleanup outcome** — `run_automatic_storage_retention` has zero Doctor visibility (confirmed absent by grep); a user has no way to see "cleanup last ran, succeeded/failed" from Product Health today.
2. **`storage_cleanup_history`'s own `MAX_STORAGE_CLEANUP_HISTORY_ITEMS = 30` constant is misleadingly named** — it bounds only the read-API page size and a purge-batch processing chunk size, never the underlying table itself, which has no row-deletion path anywhere. Growth is slow (roughly one row per automatic pass — daily or weekly — plus manual previews) and each row is small; at this rate it would take years to become materially significant, so it is disclosed here rather than fixed under this milestone's "no hypothetical future scale" instruction.

Advanced diagnostics (byte counts, paths) remain gated behind the existing "Advanced diagnostics" disclosure convention; ordinary product surfaces stay plain-language, confirmed unchanged by this milestone.

## Backup interaction

Backup architecture is already accepted and was not reopened. Verified integrated behavior:

- **Current backup location, staleness, failure, interrupted-restore:** all real and Doctor-visible (see above).
- **Backup disk consumption:** genuinely real and currently large in this dev checkout (see below) — but **not** double-counted into `StorageSummary`'s disk-pressure accounting; a real install would only notice backup-driven pressure indirectly, through raw OS free-space shrinking, never through a message naming backups specifically. Disclosed as a known, accepted design choice (`docs/appliance-storage-privacy-recovery-v1-contract.md:64-66`), not reopened.
- **Backup retention:** confirmed, precisely, to be **absent by deliberate, documented design** — `docs/local-backup-recovery-design.md`'s own Non-goals section and the accepted Aug-23 contract both state this outright ("No backup auto-pruning — confirmed intentional... not a gap, left as-is"). Grepping `backup.py` and every API caller for any deletion/capping logic returns zero matches; there is no `DELETE .../backups/...` route anywhere. This is a real, disclosed, pre-existing product decision this milestone did not re-litigate.
- **Backup visibility in Doctor:** real (staleness/unreadable-count/interrupted-restore).
- **Low-space interaction:** no disk-space precheck exists before a backup write; a real `OSError` (disk-full) propagates and is caught by the existing, already-tested exception path, which cleans up its own temp files and leaves no partial `.mbbackup` under a trusted final name — proven by the existing (not new) `create_backup` exception-handling test coverage, whose injected-exception shape is exactly what a real ENOSPC would produce.
- **Retention + backup interaction:** structurally impossible for retention to touch a backup (zero code-level coupling, confirmed by grep across both `storage/` and `repository/`), and a `.mbbackup` is a fully self-contained physical copy (DB + all discovered media, verified via direct `zipfile` inspection of real archives in this checkout) — so retention deleting live media after a backup was taken has no effect on that backup's own restorability. One fact worth naming for whoever next touches either subsystem: a full backup **does** archive the 14-day recovery quarantine directory's own contents (proven by an existing test) — quarantined-but-not-yet-purged media rides along in backups, a `backup.py`-side fact, not a retention decision.
- **A backup that silently consumes the whole disk is not healthy backup behavior — is that true here?** Empirically, yes in this dev checkout: `data/backups/` (this WSL repo) holds 156 files / 6.1 GB, and the real Windows dev root's own `userdata/data/backups/` holds 1.6 GB against a 4.6 MB live database. **Root-caused, not merely observed** (see next section) — both are explained precisely and neither is a live, currently-active leak.

### Why `data/backups/` (WSL dev repo) reached 156 files / 6.1 GB — root-caused

`.mbbackup` files are full physical copies (SQLite online-backup + every discovered media file, confirmed by direct `zipfile` inspection: one real archive contained 845 entries including a 15.75 MB `database.sqlite3` and hundreds of media files). A new backup is created automatically exactly once per genuine schema migration (never on ordinary startup against an already-current schema — gated by literal code, `if version < CURRENT_DATABASE_SCHEMA_VERSION:`), and this project bumped its schema roughly 20 times across the observed five-week window. The default backup root is a **plain relative path** (`data/backups`), resolved against whatever the process's CWD happens to be — which, for a real packaged install, is deliberately `chdir`'d to the real runtime home before any repository/backup code runs, but for a direct dev-checkout launch (`python -m mockingbird` with no `MOCKINGBIRD_HOME` override) resolves to this repo's own `data/` directory by the same, intentional mechanism.

`git log` on `tests/conftest.py` fixes the real, dated, **now-closed** cause precisely: an autouse pytest fixture has isolated `db_url`/`media_root` since 2026-08-11, but did not additionally cover `MOCKINGBIRD_BACKUP_ROOT` until Release Engineering Foundation v1 closed that gap on 2026-08-25 — any test in that 2-week window that triggered a real migration (even one whose own DB otherwise lived safely in a temp directory) could deposit one real backup into this repo's `data/backups/`. **Empirically reproven this milestone**, not merely inferred: running the full real backup test suite (31 tests) today produces **zero** new files and **zero** byte change in `data/backups/`. The remaining, more-recent files are consistent with genuine direct dev-server launches from this checkout (an intentional, documented dev-ergonomics behavior, not a bug) — something a real packaged Windows installation, which always anchors to `%LOCALAPPDATA%\MockingBird`, structurally cannot reproduce at this rate.

This rests on the same real, underlying, already-accepted product decision named above ("no backup retention policy exists, by design") — which is why a long-lived real installation would eventually feel slow backup accumulation too, just on a years-not-weeks timeline (infrequent real schema upgrades, not dozens of daily process launches). Not a new gap; already disclosed and accepted, confirmed still accurate.

## Fix implemented

**`scripts/deploy_windows_dev.py`: the runtime/model/BioCLIP-model cache is never garbage-collected — the single largest consumer found in this entire investigation (38.5 GB, including 6.25 GB of definite orphaned-staging/stale garbage), and the dominant, dated, directly-quantified driver of the observed Windows free-space decline.**

This gap was already known and disclosed at design time (`docs/windows-dev-deployment-design.md`'s own "Left for follow-up" section, quoted above) but judged "unlikely to matter in practice" — a judgment this milestone's real measurement falsifies. Fixed with a new `gc_cache_command`/`--gc-cache` CLI flag (`scripts/deploy_windows_dev.py`), implementing exactly the shape that document already named as the natural follow-up:

- Removes every runtime/model/BioCLIP-model cache entry no **currently-on-disk** retained release directory still references (an already-cleaned-up ledger entry's hash is never treated as referenced — mirrors `cleanup_releases`'s own convention exactly).
- Unconditionally removes every orphaned `.staging-*`/`.stale-*` leftover, regardless of whether its hash prefix happens to still be in use under its own bare-named entry — these suffixes are never a trusted, reusable path by construction (`ensure_cache`), and are what a killed `powershell.exe` interop call (a real, repeatedly-observed failure mode of this exact tool, per this project's own session history) leaves behind.
- Never touches `releases/` or `userdata/` (bounded, safety-tested — see "Tests," below).
- A removal failure (a file still locked by a running process) is skipped, not raised, matching `ensure_cache`'s own existing "best-effort only" precedent for exactly this situation.
- Composes with the pre-existing `--cleanup`/`--keep` flag in one invocation (cleanup runs first, so a release directory just removed no longer holds its own cache entries referenced).

**This is dev/QA tooling, not shipped product code** — confirmed by direct grep that nothing under `src/mockingbird/` imports `scripts/deploy_windows_dev.py` — so this fix does not change schema, product behavior, or anything a real end-user install does; it only closes a real, measured, disk-consuming gap in the tooling this project's own development process depends on to keep doing real-hardware acceptance work at all.

**Findings deliberately disclosed, not fixed, this milestone** (each named precisely above, each real, none release-blocking):

- Imported/folder-imported media is over-retained relative to its own documented contract (safe direction — no data loss; fixing eligibility logic safely needs new test coverage this milestone did not have time to build responsibly).
- A `"staging"` (interrupted) cleanup batch can only ever be restored, never purged (disk-space-only, restore always works).
- `storage_cleanup_history` has no row-deletion path despite its constant's misleading name (slow leak, years to matter).
- No Doctor signal for automatic-cleanup outcome.
- No orphan-media (file→no DB owner) detection anywhere (structural, low-materiality, already-disclosed-adjacent).
- Camera Node journald has no configured size bound, and the Camera Node's outbound transport-retry has no maximum duration — **both pre-existing, already-disclosed, deliberate scope decisions from earlier accepted milestones** (`scripts/install_camera_node.py`'s own comment explains the journald decision explicitly), re-confirmed still accurate, not new and not this milestone's to reopen.
- `~100 lines of confirmed-dead, deliberately-retired code` in `cleanup_saved_preview_media` (a fully retired feature, tested as retired) — harmless, not a behavior defect, out of this milestone's actual scope (no storage/retention behavior depends on it).
