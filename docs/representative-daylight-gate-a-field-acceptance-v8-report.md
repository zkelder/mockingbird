## RTT calibration field proof

**796 RTT-bounded calibration batches were attempted this session -- 0 valid, 796 `insufficient_samples`, 0 `inconsistent_samples`, 0 clock jumps.** This is the headline finding of the session and directly limits what follows.

**Root cause, precisely identified and independently confirmed three ways, not merely inferred:**

1. The reference Camera Node's own live `GET /node/v1/health` response (queried directly, both before and after the session) contains **no** `node_receive_time`/`node_time` fields at all -- the exact two additive fields the accepted RTT-Bounded Clock Calibration v1 milestone added to that response. Every RTT-bounded batch this session therefore had `node_response_at = None` for every one of its 5 concurrent attempts, which the calibration module's own sample-rejection rule excludes before the >=3-valid-sample check can ever pass -- exactly the designed "honest degradation... never a crash" path, working as specified.
2. `grep -rl node_receive_time /opt/mockingbird-camera-node/` on the Pi itself (via `ssh mockingbird-pi`) returns nothing -- the string does not exist anywhere in the Node's installed code.
3. The Node's own install manifest (`/opt/mockingbird-camera-node/manifest.json`) records `git_commit: baf9fdb838919825dfe70365305eb4722781621c`, `built_at: 2026-08-27T02:50:03Z` -- verified via `git merge-base --is-ancestor` to be a real ancestor of the current accepted HEAD, **69 commits behind**. `git log -S"node_receive_time" -- src/mockingbird_node/` shows the field was introduced in commit `bc6d5ee` ("Camera Node <-> Host RTT-Bounded Clock Calibration v1: calibration exchange..."), which post-dates `baf9fdb` by dozens of commits. The Node has not been redeployed since the "Camera Node Upgrade & Compatibility Recovery v1" milestone (2026-08-26) -- five field-relevant milestones accepted since then (v6, v7, Gate A Measurement Closure v1, the one-way Clock Normalization v1, and RTT-Bounded Clock Calibration v1 itself) never touched the physical Node.

**This is an infrastructure/deployment gap, not a code defect.** The calibration logic behaved exactly as designed under a Node that predates the protocol it depends on. It was **not fixed live**: doing so would have required restarting/redeploying the Camera Node's own service mid-session, which (a) risks exactly the "force a reconnect" action this milestone's own governing brief explicitly prohibits, and (b) would have contaminated the already-collected measurements (Section 34's own bar). See "Defects" and "Gate A closure assessment" for the precise, disclosed follow-up this implies.

Batches fired far more often than the documented 5-minute periodic cadence would alone produce (796 over 158.2 minutes averages one every ~11.9 seconds). Traced to source: the Camera Node's own analysis-stream transport is not one persistent connection -- `camera_node_live.py` explicitly documents "a fresh HTTP connection under the same provider_generation" as "a benign transport reconnect," incrementing `transport_reconnect_count` on every new connection. Since the RTT-recalibration-due check treats *any* change in that counter since the last batch as a reconnect trigger, and this Node's own analysis-stream reconnects roughly every tick, the reconnect trigger dominates the periodic one in this environment. Zero "reconnect" lines appear in the structured log (`grep -ci reconnect` = 0) -- confirming this is benign, silent, connection-level cycling, not a real instability the operator would otherwise notice. This is real, useful field evidence about how the recalibration cadence actually behaves under this Node's real transport architecture, distinct from the insufficient-samples root cause above.
