## Executive summary

This milestone did **not** start from a greenfield multi-camera problem. A prior milestone, **Camera / Source + Multi-Camera Maturity v1** (2026-08-23, commit `f97598e`, schema 46→47, confirmed a real ancestor of this milestone's starting HEAD), already built a conservative cross-camera duplicate-encounter association engine, Camera/Source/Area vocabulary, provider-compatibility tiers, and health WAN-vs-camera disambiguation. `docs/release-execution-state.md`'s Lane F had not been fully reconciled to reflect that this foundation exists (no `-report.md` for that milestone, only a `-contract.md`) — this report closes that documentation gap as part of its own reconciliation, rather than re-building what already exists.

This milestone's job — per Lane F's own framing ("need integrated acceptance for... duplicate/cross-camera behavior") — was the **integrated, whole-product experience** on top of that foundation: making Today, Bird Log, Place Story, Biodiversity, coverage, camera health, and the concurrent runtime genuinely camera-aware and internally consistent, not adding a second association engine.

Four rounds of parallel, bounded archaeology (persistence/association engine; Observation Engine concurrency; product-surface composition; health/coverage/roadmap) surfaced a precise map of what already worked and what didn't. The single highest-value finding — investigated, revised once after Tier 1 test evidence corrected an initial overcorrection, then revised again after the milestone's own full Tier 3 Core run caught a second, more subtle overcorrection this session's own narrower validation had missed — was that **an archived camera's history was unreachable from every discovery surface, contradicting this codebase's own documented doctrine** that archive-only removal preserves history. The fix that shipped is narrower and more principled than either earlier attempt: current-active-observatory *defaults* are deliberately preserved exactly as already tested and accepted, on **every** discovery surface without exception — Bird Log's own overview, Wildlife Insights, Biodiversity, **and** Place Activity Report/Today (the second correction; a pre-existing, deliberately-authored test in `test_place_change_summary_repository.py` explicitly locks this in, and the full Core run is what surfaced it — see "Validation"). What was actually missing was any way to *reach* an archived camera's real history at all, which now exists via an explicit camera filter/`source_ids` selection everywhere that concept already applies, plus two genuinely unconditional cases where no existing test disagreed and the "history" framing is unambiguous either way (Place Story's own timeline, and research/conservation export's "everything" default).

## Product contract

Per the milestone's own governing boundary: **single-Place, multi-camera**, not multi-site. Nothing in this milestone introduces a `PlaceModel`, cross-Place aggregation, or fleet concept. Place-wide surfaces (Today, Bird Log, Story, Biodiversity) remain the one authoritative view of one Place; camera-specific views are a *filter* on the same truth, never a second product.

## Source / camera identity

- Human camera names are used everywhere already-audited (Today, Bird Log, Story, camera health/roster, the new "By camera" breakdown, the new per-highlight camera attribution). One raw-UUID exposure remains, in a technical/debug row on `StreamsPage.tsx` (`Source ID: {selectedSourceId}`), not a normal-user-facing label — recorded, not fixed (out of this milestone's bounded scope; it is a setup-time technical detail, not a discovery-surface identity gap).
- **Camera rename:** already fully retroactive by construction (every consumer does a live join to `CameraSourceModel.name`, never caches/snapshots it) — proven directly in the product-shaped scenario test (renaming "Camera 1" → "Front Feeder" mid-scenario, then re-running Today, shows the new name with zero duplication).
- **Camera archival:** archive-only removal (no delete endpoint exists for a Source or Stream) was already correctly documented as preserving the underlying `Visit`/`Event`/evidence rows. This milestone found and fixed the actual gap: several **read** surfaces were unconditionally excluding an archived Source's Streams from their Visit-enumeration queries, making that preserved history genuinely unreachable. See "Bird Log / Story" and "Duplicate-inflation safety" below for the precise, principled fix.
- **New:** `RepresentativeEvidence` (the one canonical evidence-selector response object shared by Today and Bird Log) now carries `stream_id`/`stream_name` — "which camera produced this evidence," populated once at the shared selector and inherited by every consumer automatically, never a per-surface re-derivation.

## Place-wide vs. camera-specific behavior

No second product was built. The existing distinction already present in the codebase — Place-wide totals/taxa vs. a `source_ids`/`stream_id` filter parameter — was extended, not duplicated:

- **Today / Place Activity Report:** the unfiltered default correctly stays current-active-observatory-only (matching Bird Log's own default exactly, confirmed by a real pre-existing test — see "Validation"); `PlaceActivityReportRequest.source_ids` (pre-existing) now additionally reaches an explicitly-named archived Source's real historical activity for a period that predates its archival, closing the one genuine gap (there was previously no way to reach it at all, filtered or not).
- **Bird Log:** the per-species drilldown already had a `stream_id` filter; the overview (species list) did not. Added `stream_id` to `WildlifeJournalOverviewRequest`/the `GET /api/bird-log/journal` route/the API client/the existing "Stream" `<select>` control (already rendered on both overview and drilldown — it simply wasn't wired to the overview's own fetch).
- **Zone Insights** already had `stream_id`/`source_id` filters; unaffected by this milestone except for its aggregate coverage fix (below).

No new filter UI pattern was invented. A real, disclosed inconsistency was found and *not* consolidated this pass — see "Remaining major PRODUCT opportunities."

## Today

Today's backend (`place_activity_report`) already unconditionally computed `activity_by_source`/`source_quality_signals` on every call; `TodayReportPanel.tsx` rendered **none** of it. This was the single highest-leverage, lowest-risk fix available — closer to "surface it" than "build it":

- New compact **"By camera"** section, gated to appear only once 2+ cameras have activity in the period (Today stays a report, never a camera-monitoring dashboard, per the milestone's own explicit instruction). Reuses `SourceActivityList` — extracted out of `PlaceActivityReportPage.tsx` into its own shared component (`web/src/components/SourceActivityList.tsx`) specifically so this is one canonical per-camera bar-list presentation, not a second, drifting one.
- New per-highlight **"via {camera name}"** attribution on each species highlight, gated the same way, sourced from the newly-added `RepresentativeEvidence.stream_name` (see "Source / camera identity").
- **Deliberately not built:** "cameras needing attention" was *not* duplicated into the report panel. `LiveCameraOverview` already renders this, immediately adjacent on the same Dashboard page — folding a second copy of camera-health facts into the wildlife-report panel would have been redundant, not a gap.
- **Dashboard-level (not report-level) addition:** "Cameras needing attention" now distinguishes "some cameras need attention" from "**every currently-armed camera** needs attention" — the latter gets an elevated, distinct message ("MockingBird is not currently observing visually — every armed camera needs attention") and an `alert`-tone pill instead of `review`-tone. Computed purely from two already-returned facts (`today.observation_health.length` vs. `summary.headline.monitored_stream_count`) — zero new backend computation, zero schema.

## Bird Log / Story

- **Bird Log:** camera filter now reaches the overview list, not just the per-species drilldown (see "Place-wide vs. camera-specific behavior"). An explicit `stream_id` selection also now correctly bypasses the current-active-only default so an archived camera's real history is reachable by name — see "Duplicate-inflation safety."
- **Place Story:** confirmed, by direct test, that first-seen/new-species semantics are correctly Place-level by SQL construction (a `GROUP BY reviewed_label` with no per-Stream grouping), not per-camera-scoped by accident — a species Camera B sees after Camera A already confirmed it does *not* manufacture a second Place-wide first-seen event. Confirmed a since-archived camera's own past Story entries (e.g. a `first_seen` event) are **not** retroactively erased by later archival — Place Story is explicitly "a living history," and no test locks in current-active-only framing for it (unlike Bird Log/Biodiversity), so this milestone's fix applies unconditionally here.
- **Not built this pass:** `PlaceStoryEvent.source_id` exists on the dataclass/schema but is populated only for `feature_change` (place-kind) events — every wildlife-kind event (`first_seen`, regularity transitions, diversity milestones, overall-activity) leaves it `None`. Investigated the real fix: `compute_first_seen_events` and friends consume `SpeciesHistoricalStatus`, a dataclass built from a SQL `MIN(EventModel.started_at)` aggregate with no accompanying "which row produced this minimum" reference. Populating source attribution correctly would mean restructuring that shared aggregation (used by Bird Log/Today/Biodiversity alike), not threading a field through — a genuinely separate, non-trivial data-modeling exercise. Recorded as a real, identified, deliberately-deferred gap rather than forced through at the tail of this milestone.

## Coverage semantics

The most concrete "camera-hours vs. elapsed-Place-time" finding in this milestone: **both a correct and an incorrect implementation of Place-wide coverage already existed side by side in the same file**, `product_repository.py`.

- **Correct (reused everywhere else):** `_place_activity_coverage_summary` / `_monitoring_exposure_intervals_and_history` — a real interval *union* across every in-scope Stream ("was this Place being watched by any camera at this moment"), already powering Today/Place Activity Report and (via that same function) research/conservation export's live-monitoring-effort figure. Its own docstring already named the divergence below as a known, deliberately-unresolved gap at the time it was written.
- **Incorrect, now fixed:** Zone Insights' own aggregate exposure figure (`zone_insights`'s `aggregate_exposure`) was a naive per-Stream `sum()` of `healthy_seconds` — two cameras both "on" for the same overlapping hour counted as 2 hours, not 1. Fixed by migrating that one aggregate onto `_place_activity_coverage_summary`, unchanged for the single-camera case (the common case; no behavior change there) and now union-correct for 2+ cameras. Proven with a new, real, measured test: two cameras with a genuinely overlapping 2-hour exposure window (1-hour real overlap) now correctly report **3 hours** of aggregate coverage, not the previous **4**.
- Per-camera coverage (`source_activity.py`'s `monitored_seconds`/`visits_per_monitored_hour`) and Place-wide coverage remain, correctly, two different denominators for two different questions — documented here explicitly per Phase 18's own instruction, not merely implemented silently.

## Per-camera activity / yield

`source_activity.py` already delivered exactly what Phase 10 asks for: coverage-normalized `visits_per_monitored_hour` alongside a raw count, an honest `data_sufficient` gate (2-hour floor) so a 3-hour camera is never silently compared against a 24-hour one, and sorting that puts under-observed cameras last regardless of raw count. This milestone's contribution was surfacing it on Today (see above) and fixing one real second-order gap it exposed: once archived Sources stopped being unconditionally excluded from the report's Stream scope (the history fix), an archived Source with **zero** activity in the requested period started appearing in `activity_by_source` as a permanent, useless "0 visits, not enough data" row — including the auto-seeded demo Source in every fresh install. Fixed at the source: an archived Source is now excluded from `activity_by_source` specifically only when it *also* has zero visits in that period — an archived camera with real activity in the period (the actual case this milestone's fix exists for) still shows correctly.

## Overlap semantics

Reused, not rebuilt (see "Existing multi-camera foundation"). This milestone's own product-shaped scenario test directly proves the full chain end to end: a real, directly-seeded `"associated"` cross-camera pair (mirroring the established test precedent in `test_place_activity_report_repository.py`) reduces a Place-wide taxon count from 3 real Visits to 2, and — a genuinely interesting, correct, previously-unverified-in-this-form detail — the deterministic lexicographic exclusion rule means the *shared* encounter's "credit" lands on whichever Visit id sorts first, so one camera's own per-camera count can legitimately be lower than its raw Visit count once cross-camera dedup is applied. This is honest, not a bug: Place-wide totals stay correct either way, and per-camera attribution of a genuinely shared encounter is necessarily a one-or-the-other choice.

No new schema, no new spatial/GIS signal, and no individual-animal-identity claim was added — matching Phase 12/14's explicit boundaries. Terminology used throughout (`"associated"`/`"possible"`, never `"confirmed"` or `"same animal"`) matches the existing engine's own vocabulary exactly.

## Concurrent runtime

Archaeology (not measurement) confirmed genuine per-Stream isolation at every layer already built: one dedicated OS thread + private asyncio event loop per `_EngineSession` (no shared pool, and — a real, disclosed fact — `ObservationEngineSessionManager.start()` has no cap on concurrent sessions at all); one independent ONNX CUDA `InferenceSession`/GPU allocation per Stream (no software-level serialization between Streams' own detector calls); a genuinely shared, correctly-serialized single-worker BioCLIP-2 auto-identification path (appropriate, since it is a real shared expensive resource, and it runs off the per-frame hot path); per-Stream bounded frame queues (4 frames) with drop-oldest + coalesce-to-newest, **already implemented and already counted** (`dropped_frames`/`coalesced_frames`/`stale_frames`) — this already-existing mechanism is exactly the Phase 24 backpressure question, not a gap to build; per-Stream Visit-authority budgets at the schema/row level, with an existing regression test for a real, historical global-singleton-authority bug (2026-08-19, now fixed).

One real, previously-unconfirmed architectural detail found and disclosed: `ProductRepository._observation_authority_lock` (a per-repository-instance `threading.Lock`) does **not** actually serialize concurrent Streams' writes in production, because each Stream's `_EngineSession` constructs its own independent `ProductRepository` instance/connection (confirmed via `main.py`'s own `get_observation_engine_session_manager` docstring). Real cross-connection write serialization, if any, falls entirely to SQLite's own single-writer behavior (`busy_timeout=5000ms`, no WAL mode configured) — a fact worth measuring, not just reading about (see below).

## Fairness / backpressure

Built and ran a new, genuine, measured concurrency test (`tests/test_multi_camera_concurrent_runtime.py`) — real `threading.Thread`s, one per Stream (matching production's own architecture exactly), each with its **own** `ProductRepository` instance/connection against one shared SQLite file (matching production's actual per-session repository construction, not the lighter shared-instance shortcut most existing engine tests use), driving the real `_EngineSession._run_assembly_tick` admission/assembly path directly (detector/transport bypassed, per this milestone's own "use deterministic fixtures, real hardware not required" instruction).

**Measured results** (this session, this sandbox, in a clean/idle state — not a formal performance benchmark; see the environmental-sensitivity note below):

- **2-camera ordinary** (10 confirmed encounters each, genuinely concurrent): both Streams completed with exactly their own 10 candidates (zero cross-Stream contamination); total wall-clock **1.40s**, below the **2.70s** sequential-equivalent bound (1.30s + 1.40s) — real concurrency confirmed, not secret serialization.
- **4-camera asymmetric** (1 busy = 40 encounters, 3 quiet = 3/5/8 encounters, all concurrent): in a clean run, every Stream produced exactly its own candidate count (zero contamination); quiet Streams completed in 0.71s/0.87s/4.13s — all well under the busy Stream's own 17.25s — proving no starvation/blocking under ordinary conditions. Per-candidate latency crept up mildly under concurrent contention (quiet-1's ≈0.24s/candidate vs. quiet-3's ≈0.52s/candidate, both doing identical-shaped work) — bounded, not indefinite.
- Along the way, this test's own fixture surfaced two genuinely real, already-correct product protections firing exactly as designed against unrealistic synthetic data — Scene Confusor Suppression's `blocked_scene_confusor_suspected` (identical bounding-box geometry reused across many synthetic encounters looked exactly like a real recurring static-scene confusor) and the real per-Stream `max_candidates_per_hour=20` authority budget (all synthetic encounters landed in the same real wall-clock hour). Both were fixture bugs in this new test, not product bugs — fixed by varying synthetic geometry/image content across a 64-cell grid and by explicitly raising the authority budget for the high-volume scenario, exactly the override mechanism that setting exists for.

**A real, measured, more significant finding: occasional lost candidate-Visit creation under real concurrent write contention.** Re-running the 4-camera test repeatedly surfaced a genuine, reproducible (roughly 1-in-3 to 1-in-4 runs) shortfall — a quiet Stream occasionally created one fewer candidate than its own workload called for, with zero exception surfaced to the caller. Root-caused via the counterfactual ledger to a real `outcome="failed"`/`reason="observation_candidate_visit_persistence_failed"` — `ProductRepository.create_candidate_visit_from_proposal`'s own defensive `except Exception` boundary (marked `# pragma: no cover` in the source, i.e. never previously exercised by any existing test) catching a `sqlalchemy.exc.OperationalError` from real concurrent SQLite writes across independent per-Stream connections to one shared file, exactly matching production's own architecture (see "Concurrent runtime," above). This is genuine dropped work (Gate A: Visit correctness), not a cosmetic issue — `candidate_visit_adapter.py`'s own caller deliberately does *not* retry a `"failed"` outcome ("record it and keep going, this adapter must never be the reason a live observation loop crashes"), so today a candidate lost this way is lost permanently, silently.

A bounded transient-retry fix (catch `OperationalError` specifically, retry up to 3 attempts with a short backoff, squarely within the method's own already-documented idempotency guarantee) was implemented and tested — then **deliberately reverted**. Repeated testing showed it did not reliably close the gap (some runs still failed after all 3 attempts) and, under a period of real competing system load (this sandbox's own background Core test run), measurably pushed some runs toward much longer wall-clock times with no better outcome. `create_candidate_visit_from_proposal` is Stage 7's live admission/persistence boundary — the single most critical write path in the product. Shipping an under-tested change there at the tail end of this milestone's own time budget, on unproven evidence, was judged the wrong call; the finding is recorded honestly (with full root-cause detail preserved in that method's own docstring) as real, measured, and deliberately not fixed this pass, rather than forced through. **This is the single most concrete, actionable item for a focused follow-on investigation** — see "Remaining major PRODUCT opportunities."

**Honestly not measured:** real GPU/CUDA-driver-level contention between concurrent ONNX inference sessions on one physical GPU. This genuinely requires real multi-camera hardware this sandbox does not have; static reading alone cannot answer it. Disclosed as an open question, not overclaimed as resolved.

**Environmental sensitivity, disclosed:** this test's own wall-clock assertions (never its correctness assertions — cross-Stream isolation held in every run observed) are sensitive to real competing CPU load on the host running it; a run started while this milestone's own full Core suite was independently consuming ~50% CPU in the background showed materially different timing than a clean run. Real evidence either way is preserved above from clean-environment runs specifically.

## Product-shaped scenario

Built and ran a real, executable, comprehensive scenario (`tests/test_multi_camera_place_experience_scenario.py`) matching this milestone's own Phase 39 brief closely: Camera A ("Camera 1" → renamed "Front Feeder" mid-scenario, busy — 4 confirmed Visits including two cardinals), Camera B ("Back Yard," lower/diverse — a squirrel plus a cardinal that overlaps Camera A's own first cardinal, seeded as a real `"associated"` cross-camera pair, then archived partway through), Camera C ("Bird Bath," quieter — one confirmed Visit), a reviewed correction applied after all of the above, and one Place Feature tied to the still-active Front Feeder camera. In one continuous test, this proves:

1. Today's per-camera breakdown shows exactly the 3 real cameras with correct names and correct (dedup-aware) per-camera counts.
2. Place-wide cross-camera dedup reduces 3 real cardinal Visits to 2 confirmed, never falsely implying 3 distinct birds.
3. Place Story's first-seen semantics stay Place-level: one `first_seen` cardinal event, not two, despite two cameras seeing it.
4. Renaming Camera A is fully retroactive with zero duplication. Archiving Camera B does not retroactively *erase* its real activity from a report period that already happened — Today/Place Activity Report's own unfiltered default correctly goes quiet on it (the same current-active-observatory framing as item 5, below), but explicitly naming it via `source_ids` still reaches its real, preserved activity for that same period.
5. Bird Log's default view correctly goes quiet on the archived camera's species (matching the existing, deliberately-tested current-active-only convention) — but its real history remains reachable by explicit camera filter, the actual gap this milestone closed.
6. Biodiversity's "as of right now" headline correctly drops a species only ever seen on the now-archived camera — a **different, deliberate** default than Bird Log's own explicit-filter escape hatch, both investigated and confirmed intentional via existing dedicated tests, not merely assumed.
7. A reviewed correction (`house_finch` → `eastern_bluebird`, via the real `revise_visit_review` truth-correction path) propagates correctly to both Bird Log and Biodiversity.
8. The camera roster stays coherent (3 real cameras, correct names, no duplicates) after every mutation above.
9. The Feature/camera link survives the rename untouched.

Deliberately not exercised in this scenario (covered elsewhere, or genuinely out of a static-fixture test's reach): live Camera Node disconnect/reconnect state-machine transitions (an `engine_runtime` concern, covered by the concurrency test and existing `test_engine_runtime.py` retry-policy tests); mobile viewport rendering (a Playwright/frontend concern).
